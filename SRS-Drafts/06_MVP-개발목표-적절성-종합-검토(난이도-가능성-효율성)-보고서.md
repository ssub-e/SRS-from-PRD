### 1.2 ⚠️ 발견: 과부하 지점 3건

#### 조정 권장 A: 쇼핑몰 연동 단계 분리

> **현재:** F2에서 카페24 + 스마트스토어 2종을 동시 구현  
> **문제:** 각 플랫폼의 OAuth 스펙, API 구조, Rate Limit 정책이 다르므로 각각 별도 학습·구현 필요  
> **권장:** Phase 1에서는 **카페24만 구현**, 스마트스토어는 Phase 1.5에서 추가

| 항목 | 절감 효과 |
|---|---|
| 개발 시간 | **1~2주 절감** |
| 학습 부담 | OAuth 스펙 학습 1회로 축소 |
| 핵심 가치 영향 | ❌ 없음 — 파일럿 2사 중 카페24 사용사가 먼저 연동되면 충분 |

#### 조정 권장 B: 멀티테넌트 MVP 단순화

> **현재:** REQ-FUNC-026 "논리적 격리(스키마)" — 테넌트별 DB 스키마 분리  
> **문제:** 스키마 기반 멀티테넌트는 마이그레이션·관리가 복잡  
> **권장:** Phase 1에서는 **tenant_id 컬럼 기반 Row-Level Isolation**으로 단순화. 파일럿 2사 규모에서는 충분

| 항목 | 절감 효과 |
|---|---|
| 개발 시간 | **1주 절감** |
| 복잡도 | DB 마이그레이션 스크립트 불필요 |
| 핵심 가치 영향 | ❌ 없음 — 데이터 격리는 WHERE 조건으로 보장. 교차 노출 방지는 API 미들웨어로 강제 |
| 전환 비용 | Phase 2에서 스키마 격리로 업그레이드 가능 |

#### 조정 권장 C: 기상청 중기예보 API 제거

> **현재:** EXT-02 "기상청 중기예보 API (3~10일 예보)" — SRS §3.1에 포함  
> **문제:** 중기예보는 단기예보와 별도 API이며, MVP 예측 모델(Prophet/LightGBM)은 주로 단기 변수를 사용  
> **권장:** Phase 1에서는 **단기예보(EXT-01)만 사용**. 중기예보는 Phase 2에서 TFT 모델 전환 시 추가

| 항목 | 절감 효과 |
|---|---|
| 개발 시간 | **0.5주 절감** |
| API 관리 포인트 | 1개 감소 |
| 핵심 가치 영향 | ❌ 없음 — 단기예보만으로 1~3일 예측 가능 |

### 2.2 기술 스택 실무 리스크

#### ⚠️ 리스크 R1: Prophet 설치 의존성

| 항목 | 상세 |
|---|---|
| **문제** | Prophet 은 내부적으로 `cmdstan`(C++ 컴파일러)에 의존. Docker 이미지 빌드 시 시간이 길고(5~10분), 이미지 크기가 큼(~1.5GB) |
| **영향** | Railway/Render 배포 시 빌드 시간 증가. 무료 티어 빌드 시간 제한에 걸릴 수 있음 |
| **대안** | MVP에서 **LightGBM 우선 사용** (설치 <10초, 이미지 ~500MB). Prophet은 별도 실험 후 필요시 추가 |
| **권장** | C-TEC-005를 **"LightGBM 우선, Prophet 선택적"**으로 조정 |

#### ⚠️ 리스크 R2: WeasyPrint 시스템 의존성

| 항목 | 상세 |
|---|---|
| **문제** | WeasyPrint는 `cairo`, `pango`, `gdk-pixbuf` 등 시스템 라이브러리 필요. 로컬 설치 시 OS별로 설치 방법이 다름 |
| **영향** | Windows 로컬 개발 시 설치 난이도 높음 |
| **대안** | Docker 개발 환경 사용 시 해결. 또는 **FPDF2**(순수 Python, 의존성 제로) 대안 검토 |
| **권장** | Docker 개발 환경을 표준으로 설정. FPDF2를 백업 옵션으로 확보 |

#### ⚠️ 리스크 R3: Streamlit 멀티유저 한계

| 항목 | 상세 |
|---|---|
| **문제** | Streamlit은 단일 사용자 대시보드에 최적화. 동시 접속 시 세션 격리, 인증 UI 커스텀이 제한적 |
| **영향** | 파일럿 2사(~5명 동시 접속)에서는 문제 없으나, 사용자 증가 시 한계 |
| **대안** | `streamlit-authenticator` 라이브러리로 기본 인증 구현. FastAPI JWT와 연계하여 세션 관리 |
| **권장** | Phase 1에서는 허용. 파일럿 종료 후 사용자 피드백에 따라 React 전환 판단 |

#### ⚠️ 리스크 R4: APScheduler 지속성

| 항목 | 상세 |
|---|---|
| **문제** | APScheduler는 인메모리 스케줄러. Railway/Render 서비스 재시작 시 스케줄이 초기화될 수 있음 |
| **영향** | 매일 16:00 알림 발송이 서비스 재시작으로 누락될 가능성 |
| **대안** | ① APScheduler의 `jobstore`를 PostgreSQL에 저장 (영속화) ② Railway의 Cron Job 기능 활용 ③ 서비스 시작 시 마지막 실행 시점 확인하여 누락 건 보상 발송 |
| **권장** | APScheduler + PostgreSQL jobstore 조합으로 영속화 필수 |

## 6. 바이브코딩 관점 재평가

> **대상 프로필:** 초급자 수준 SW 배경지식을 갖춘 4년차 IT 직무 종사자가, AI 코딩 어시스턴트(Cursor, Antigravity 등)를 활용한 **완전 바이브코딩**으로 MVP를 개발하는 시나리오.

### 6.1 바이브코딩이 바꾸는 것과 바꾸지 않는 것

| 구분 | 빨라지는 것 ✅ | 빨라지지 않는 것 ❌ |
|---|---|---|
| **코드 작성** | AI가 즉시 생성 | — |
| **표준 패턴** | FastAPI CRUD, Streamlit 차트 → 거의 즉시 | — |
| **디버깅** | — | 오류를 **이해하고 설명**해야 AI가 수정 가능 |
| **환경 설정** | — | Docker, DB 연결, 환경변수 → **맥락 특이적** 오류 많음 |
| **외부 API 연동** | — | OAuth 리다이렉트, 토큰 갱신 → **실시간 디버깅** 필수 |
| **통합 테스트** | — | 컴포넌트 연결 지점에서 오류 발생 → 경험 필요 |
| **ML 결과 판단** | — | "코드가 돈다 ≠ 모델이 맞다" → **결과 해석** 필요 |

### 6.2 컴포넌트별 바이브코딩 적합도

| 컴포넌트 | AI 학습 데이터 | 바이브코딩 적합도 | 시간 변화 (기존→바이브) | 주의점 |
|---|:---:|:---:|:---:|---|
| FastAPI 세팅·CRUD | 매우 많음 | ✅ **최적** | 2주 → **0.5주** | — |
| Streamlit 대시보드 | 매우 많음 | ✅ **최적** | 1주 → **0.5주** | — |
| SQLModel 스키마 | 많음 | ✅ 우수 | 1주 → **0.5주** | — |
| JWT 인증 + Row-Level | 많음 | ✅ 우수 | 2주 → **1주** | — |
| 기상청 API 호출 | 보통 | 🟢 양호 | 1주 → **0.5주** | 공공데이터 응답 포맷 직접 확인 필요 |
| DataLab API | 보통 | 🟢 양호 | 0.5주 → **0.5주** | — |
| LightGBM + SHAP | 많음 | 🟡 **주의** | 2주 → **1.5주** | 코드는 생성되나 **예측 결과 합리성 판단은 사람의 몫** |
| Gemini API | 많음 | ✅ 우수 | 1주 → **0.5주** | — |
| WeasyPrint PDF | 보통 | 🟡 주의 | 1.5주 → **1주** | 시스템 의존성 오류가 AI 해석이 어려운 유형 |
| APScheduler | 많음 | ✅ 우수 | 0.5주 → **0.5주** | — |
| **카페24 OAuth** | 🔴 **적음** | 🔴 **위험** | 2주 → **2~3주 ⬆️** | 한국 특화 API, 글로벌 AI 학습 데이터 부족 |
| **카카오 알림톡** | 🔴 **적음** | 🔴 **위험** | 1주 → **1.5~2주 ⬆️** | 한국 특화 API, 템플릿 심사 등 비기술적 대기시간 |
| SMS Gateway | 보통 | 🟢 양호 | 0.5주 → **0.5주** | — |
| 인원 역산 (수학) | — | ✅ 최적 | 0.5주 → **0.5주** | — |
| 폴백/예외 처리 | — | 🟡 주의 | 1.5주 → **1.5주** | 로직 설계는 사람이 해야 함 |
| 통합 테스트 | — | ❌ 변화 없음 | 2주 → **2~3주 ⬆️** | 바이브코딩 **최대 약점** |

> **코드 생성은 ~35% 빨라지나, 한국 API 디버깅 + 통합 테스트에서 시간 소모 → 총 소요는 유사하거나 +2주**

### 6.3 바이브코딩 특화 리스크 3건

#### VIBE-R1: 한국 특화 API의 AI 학습 데이터 부족

| 항목 | 상세 |
|---|---|
| **대상** | 카페24 OAuth, 카카오 알림톡, 기상청 API |
| **문제** | 글로벌 AI 모델은 Stripe/Twilio/OpenWeather 등에 훈련되어 있으나, **카페24·카카오는 한국어 문서 기반**이라 AI가 정확한 코드를 생성하지 못할 확률이 높음 |
| **증상** | AI 생성 코드가 실행은 되지만 실제 API와 **파라미터·인증 방식이 다름** → 반복 수정 루프 |
| **대응** | ① 해당 API 공식 문서를 AI에게 **직접 제공(context injection)** ② 공식 SDK 존재 시 활용 ③ 이 부분은 **튜토리얼 기반 수동 학습 병행** |

#### VIBE-R2: "코드가 돈다 ≠ 로직이 맞다" 판단 지점

| 항목 | 상세 |
|---|---|
| **대상** | ML 예측 결과 해석, SHAP 기여도 합리성, 인원 역산 정확도 |
| **문제** | AI가 LightGBM + SHAP 코드를 완벽히 생성해도, **"강수량이 높으면 우산 수요가 올라가는가?"**를 판단하는 것은 도메인 지식 |
| **대응** | ① 소규모 테스트 데이터로 **눈으로 확인 가능한 시나리오** 먼저 검증 ② SHAP 시각화를 Streamlit에 노출해서 직관적 확인 ③ 4년 IT 경력의 **도메인 이해력을 레버리지** |

#### VIBE-R3: 환경 설정 지옥 (Environment Hell)

| 항목 | 상세 |
|---|---|
| **대상** | Docker, PostgreSQL 연결, WeasyPrint 시스템 라이브러리, Railway 배포 |
| **문제** | 환경 설정 오류는 OS·버전·경로에 따라 원인이 다양하여 **AI가 틀린 해결책을 제시할 수 있음** |
| **대응** | ① **Docker를 개발 환경 표준으로 강제** → OS 차이 제거 ② Dockerfile을 초기에 완성한 후 모든 개발은 컨테이너 내에서 진행 ③ Railway 배포 = Docker 이미지 기반 → 로컬 ≈ 배포 환경 일치 |
